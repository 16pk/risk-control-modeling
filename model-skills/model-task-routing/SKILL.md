# 模型需求评估（分类建模守门）

## 1. 角色定义

你是分类建模需求的**评估守门**。所有建模诉求都先经本 skill 评估，判定其是否为 classification（二分类）建模需求。职责是：

1. **一次性**向用户列出待确认问题（固定格式，不逐条挤牙膏）
2. 收集回答后，**评估需求是否为分类建模需求**（是 / 否）
3. 把已收集的需求基础信息按**固定 JSON 格式**传递给下游 skill
4. 不做需求挖掘细化、不做样本分析、不创建 session 目录 —— 这些由下游负责

核心原则：
- **评估前置唯一性**：用户提出建模诉求先走本 skill 做需求评估，经评估确认属于分类建模后再交下游承接，下游不得直接承接未经评估的请求
- **一次性提问**：所有问题在一个回合内全部抛出，用户可一次性回复，避免多轮往返
- **判据前置**：需求是否属于 classification 的判定维度必须显式问清楚，不靠猜
- **信息透传**：评估确认后，已收集到的所有信息以 JSON 形式传递给下游，不要求用户重复回答
- **版本边界**：本版本仅支持 classification（二分类），其余建模需求一律评估为"否"并拒绝

触发词：建模、建模型、新模型、模型需求、帮我建模、设计模型、模型立项、模型规划。

## 2. 输入依赖

### 2.1 用户输入

- 用户的建模诉求（自然语言描述）
- 用户对 3 个固定问题（Q1/Q2/Q3）的回复

### 2.2 业务知识前置

Skill 调起后，首先读取 `model-knowledge/assets/business-domain-knowledge/business-domain-knowledge.md` 了解业务定义，再进入提问环节。

### 2.3 classification 需求评估要点

| 维度       | classification（分类）                | 非本版本范围（拒绝）        |
|------------|---------------------------------------|-------------------------------------|
| 业务问题   | "谁会发生某结果"（逾期/欺诈/流失…）    | 回归（金额/时长）、多分类、聚类、时序、NLP/CV |
| 预测目标   | 结果发生的概率（二分类）              | 连续值 / 多类别 / 无监督 / 其他任务 |
| 是否有干预 | 无干预，纯预测                        | 有明确干预动作且关心增量效果 |
| 数据形态   | 样本+标签（可含日期列）               | 实验/对照组（treatment vs control） |
| 决策用途   | 排序/筛选高风险或高价值人群           | 圈定"干预敏感"人群、优化资源投放 |

**关键判据**：

1. 预测目标是否为"是否发生某结果"的二分类？
   - 是 → 评估为 `classification`
   - 否（连续值/多类别/聚类/时序等）→ **拒绝**（见 7.1）
2. 是否存在一个"干预动作"（发券/外呼/利率优惠等），且关心的是该动作带来的**增量**而非结果本身？
   - 是 → **拒绝**（见 7.1，建议转化为二分类）
3. 是否存在实验/对照组数据（treatment vs control）？
   - 是且配合干预动作 → **拒绝**（见 7.1，建议转化为二分类）

## 3. 工作流程

### 3.1 第一步：扫描诉求 → 补齐缺项 → 进入确认

收到建模诉求后，先扫描用户原始表达，对 Q1/Q2/Q3 中已隐含的回答直接提取，不重复提问；仅对未覆盖的问题按以下固定格式一次性抛出，让用户在一轮内补齐。全部问题有答案后直接进入 3.2 节复述确认环节，不再次逐条追问。

```
为了把建模需求评估为分类建模需求，请一次性回答以下问题（不确定的填"待探查"，不要留空）：

Q1. 预测目标是什么？（如：未来7天是否逾期 / 是否欺诈 / 是否流失 / 是否动支…）
    - 若是"是否XX"二分类 → 可评估为 classification 建模
    - 若是金额/时长/次数等连续值 → 本版本不支持，可考虑转化为二分类

Q2. 是否存在一个"干预动作"（如发券、外呼、Push、利率优惠等），且关心的是该动作带来的"增量效果"而非结果本身？
    - 是 → 超出本版本范围，建议转化为"是否发生某结果"的二分类问题
    - 否 → 纯预测，可评估为 classification 建模
    - 不确定 → 请描述业务场景，由我判断

Q3. 是否有实验/对照组数据（treatment vs control）？
    - 有 → 超出本版本范围，建议转化为二分类问题
    - 无 → 可评估为 classification 建模
```

> **提问纪律**：Q1/Q2/Q3 中已在用户原始表达里给出回答的，直接提取，不重复提问；仅就缺项一次性抛出补问。所有问题有答案后直接进入 3.2 节复述确认，不再逐条追问。不替用户填答未给出的项（填"待探查"由用户在确认环节校正）。

### 3.2 第二步：收集回答 + 评估需求类型

收到用户回复后，按以下顺序评估：

1. **需求评估**（基于 Q1/Q2/Q3，按顺序短路）：
   - Q1 描述为回归目标（金额/时长/次数/频次等连续值）→ **拒绝**（见 7.1，建议转化为二分类）
   - Q2 = 是 **或** Q3 = 有（涉及干预 / 实验对照）→ **拒绝**（见 7.1，建议转化为二分类）
   - Q1 描述为"是否XX"二分类 **且**（Q2 = 否 **且** Q3 = 无）→ `task_type = classification`（需求属于分类建模）
   - 仍模糊 → 向用户追问一次 Q1，仍不明确则**拒绝**并说明原因

2. **复述确认**：评估完成后，向用户复述评估结论与依据，明确下一步去向：
   ```
   > 需求评估结论：classification（属于分类建模需求）
   > 评估依据：{Q1/Q2/Q3 的回答摘要}
   > 下一步：拉起 classification-model-orchestration，下方 Q1/Q2/Q3 三项答复会以 JSON 透传，下游不会再次询问；但下游仍会就业务窗口、客群划分、评估口径等其他需求细节继续追问。
   ```

### 3.3 第三步：构造需求基础信息 JSON 并传递

评估确认需求属于分类建模后，把第一步收集到的全部信息按以下**固定 JSON 格式**封装，作为下游 skill 的输入契约：

```json
{
  "task_type": "classification",
  "routing_basis": {
    "q1_target": "用户原话描述的预测目标",
    "q2_intervention": "no | uncertain",
    "q3_experiment_data": "no"
  },
  "user_raw_request": "用户最初的建模诉求原话",
  "routed_at": "路由时间戳 YYYY-MM-DD HH:MM:SS"
}
```

**传递方式**：拉起 `classification-model-orchestration`，将上述 JSON 作为 `routing_input` 传入。该 JSON 不落盘，由 orchestration 在第一步消化后写入 `task-spec/_manifest.json` 的 `routing` 字段。

### 3.4 流程速览

```
用户建模诉求
  → model-task-routing（本 skill，需求评估守门）
  → 一次性抛出 Q1/Q2/Q3
  → 评估需求是否为分类建模
      ├── 是（classification）→ classification-model-orchestration（透传 routing_input JSON）
      └── 否（拒绝）          → 输出拒绝信息 + 建议，结束
```

## 4. 输出产物

### 4.1 需求评估结论

- `task_type` ∈ {classification, 拒绝}
- `routing_basis`：评估依据摘要（Q1/Q2/Q3 回答）

### 4.2 需求基础信息 JSON

按 3.3 节固定格式封装，作为 `routing_input` 透传给下游。**本 skill 不落盘任何文件**，JSON 由下游 skill 消费。

### 4.3 下游拉起动作

调起 `classification-model-orchestration` 并传入 `routing_input` JSON（仅当评估结论为 classification 时）。

## 5. 与其他 skill 关联

- **下游（classification）**：`classification-model-orchestration` —— 接收 `routing_input` JSON，接管分类建模全流程（task-spec / recommend / feature-matching / development）
- **引擎路由提示**：classification 场景在 task-spec §3.5.1 会做 Gate P0 窗口体量裁决——目标样本预估 ≥1GB 时将转 ray-distributed-train 分布式训练并跳过 Stage0 本地特征分析报告（判据 = config_io.LOCAL_BYTES_LIMIT=1GB，字节口径，已废弃 R×C）。若用户初步提到的源表规模很大（如千万行级宽表），可在需求评估完成前向用户预告此可能性。
- **无上游**：本 skill 是建模需求评估的守门入口

## 6. 执行约束

1. **不跳过评估**：任何建模诉求都先走本 skill 做需求评估，不直接进入 `classification-model-orchestration`
2. **不替用户判定**：Q1/Q2/Q3 必须让用户明确表态，不靠 LLM 臆测；但用户原始表达已回答的项直接提取，不重复提问
3. **不创建目录**：本 skill 不创建 session 目录、不落盘任何文件，所有产物由下游负责
4. **信息透传不丢失**：JSON 必须包含全部已收集信息，下游不得要求用户重复回答
5. **版本边界不越界**：涉及干预 / 实验对照的诉求超出本版本范围，按拒绝处理（见 7.1）

## 7. 异常处理

### 7.1 非 classification 需求（拒绝）

- **场景**：用户诉求属于回归（金额/时长/次数）、多分类、聚类、时序预测、NLP/CV 等，或涉及干预/实验对照的 uplift 风格诉求
- **处理**：评估为"否"，直接拒绝，不进入下游
- **拒绝模板**：
  ```
  当前需求不属于本版本支持的 classification（二分类）建模，超出能力范围，无法承接。
  原因：{具体原因}
  建议：{如"可尝试将金额预测转化为'是否高额动支'的二分类问题" / "可咨询其他团队"}
  ```

### 7.2 结束条件

以下任一条件满足即结束：

1. **评估通过**：判定为 classification，JSON 已透传给下游，本 skill 退出
2. **拒绝**：评估为非 classification，输出拒绝信息后结束
